# Controlling Excel Variance Analysis

A real, tested Excel controlling workbook — budget-vs-actual variance
analysis, a monthly trend view, a year-over-year comparison, and an
ad-hoc exception report — built to close a specific gap for Hofpfisterei's
"Werkstudent im Bereich Controlling" posting: "sehr gute Kenntnisse in
Excel", "Erstellen von Reports als Standard oder auch ad-hoc Auswertungen",
and support for "Jahresbudgetplanung und Jahreszielfindung".

## What this is, precisely

- `src/generate_data.py` — generates a synthetic but realistic 24-month
  (2025–2026) controlling dataset for a mid-size company shaped like a
  bakery/retail business: 9 cost centers (production, retail stores,
  logistics, purchasing, admin, marketing) × 7 cost accounts
  (Personalkosten, Materialaufwand, Energiekosten, etc.) = 1,512 rows,
  each with a budget figure and an actual figure. The generator injects
  real, deliberate signal, not just random noise: a sustained fuel-cost
  overrun in Logistik starting April 2026, a one-off equipment-repair
  spike in Produktion Backwaren in March 2026, and a consistent ~12%
  underspend in Marketing — so the variance analysis has something real
  to find, the same way the nlp-transformer-training-ablation project's
  dataset redesign was fixed to avoid a too-easy, signal-free result.
- `src/build_workbook.py` — builds `controlling_report_2025_2026.xlsx`
  with five sheets: **Rohdaten** (raw fact table), **Kostenstellen-
  Uebersicht** (budget vs. actual by cost center, with conditional
  formatting flagging >10% deviations), **Monatsverlauf** (budget vs.
  actual by month), **YoY-Vergleich** (2025 vs. 2026 by cost center),
  and **Abweichungs-Report** (every cost-center/account/month
  combination where the deviation exceeds both 15% and €500, sorted by
  absolute deviation — an ad-hoc exception report a controller would
  actually use).

## Why formulas, not openpyxl's native PivotTable object (read this before citing)

Excel's real "pivot table" is normally built by pointing Excel at a data
range and letting *Excel itself* construct the pivot cache and layout.
openpyxl can write a `PivotCacheDefinition`/`PivotTable` XML structure
programmatically, but producing one that Excel opens cleanly and
refreshes correctly from a cold, non-Excel-authored write is unreliable
in practice — there is a real risk of shipping a workbook that looks
right in the XML but Excel refuses to open or refresh cleanly.

Instead, every summary sheet here is built with live `SUMIFS` and
`SUMPRODUCT` formulas against the raw data range — the same day-to-day
"ad-hoc Auswertung" work a controller does directly in Excel, and fully
verifiable: I don't have to trust that the formulas are correct, I
tested that they are. This is the same honest substitution pattern as
`powerquery-sap-reporting`'s disclosed lack of real Power Query
execution — a different tool, chosen because it's the one I can
actually verify end-to-end in this environment, not because it's
strictly identical to what a native pivot table would produce.

## How this was actually verified (not just "the script ran")

The test suite (`tests/test_workbook.py`, 10/10 passing) does not just
check that openpyxl wrote plausible-looking formula strings. It:

1. Regenerates the source data independently.
2. Builds the workbook.
3. **Forces LibreOffice Calc — a real, independent spreadsheet engine,
   not openpyxl — to open the file headless and recalculate every
   formula**, then re-saves it.
4. Reads back the *recalculated* values (not the formula strings) and
   cross-checks every cost-center total, monthly total, and YoY figure
   against an independent pandas `groupby().sum()` computation of the
   same raw data.

This matters because a static check ("does the formula look
syntactically right") would not catch a formula that parses but computes
the wrong aggregation, or a formula LibreOffice/Excel can't evaluate at
all. Running it through a real spreadsheet engine and checking the
computed output is what actually proves the workbook works.

Tests also confirm: the deliberately-injected Marketing underspend shows
up as a genuine >8% negative deviation (not noise), the one-off
equipment-repair spike is correctly flagged in the exception report, and
the exception report is correctly sorted and threshold-filtered.

## Honest limitations

- All data is synthetic, generated by a seeded PRNG — not real
  Hofpfisterei or bakery-industry data, which I have no access to.
- No SQL Server / OLAP source system feeds this workbook — it's a
  standalone Excel deliverable. (A separate project,
  `sql-olap-controlling-reporting`, covers the SQL Server/OLAP side of
  this posting's requirements.)
- No genuine annual budget-planning *process* (target-setting,
  negotiation, approval workflow) is modeled — this is the reporting/
  variance-analysis side of controlling, which is what the posting's
  "Erstellen von Reports" and "ad-hoc Auswertungen" bullets actually
  ask for; "Jahresbudgetplanung" as a negotiation process is not
  something a solo project can honestly simulate.

## Running it
